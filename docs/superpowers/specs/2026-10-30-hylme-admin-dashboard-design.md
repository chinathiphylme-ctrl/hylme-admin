# Hylme แอดมินรายวัน — เอกสารออกแบบ

วันที่ 30 ต.ค. 2026 · ต้นแบบที่ตกลงแล้ว: https://claude.ai/artifact/BAGQzEMXjHPJMRbhYpvSBN

## 1. เป้าหมาย

เว็บแยกสำหรับทีมแอดมิน Hylme (พี่ก้อย, นุ่น) และเจ้าของ ใช้ดูสรุปแชทรายวันจากแท็ก Pancake ของ 4 เพจ
เพื่อเห็นว่าลูกค้าติดตรงไหน ควรแก้ตรงไหนก่อน และแชทไหนต้องตามวันนี้

สำเร็จเมื่อ:
- แอดมินอัปโหลดไฟล์ export ของเมื่อวานได้ในไม่กี่คลิก แล้วหน้าภาพรวมอัปเดตทันที
- ตัวเลขบนเว็บตรงกับไฟล์ export (ทดสอบกับข้อมูล 29 ต.ค.: ทุกเพจ แชทใหม่ 188 ปิด 27 · FB 118/8 · ไขมัน 70/19)
- ดูย้อนหลังและเทียบช่วงเวลาได้ แยกตามเพจได้
- ไม่มีชื่อ เบอร์โทร หรือเนื้อหาข้อความของลูกค้าเก็บอยู่ในระบบ

## 2. ขอบเขต

**มีใน v1**
- หน้า ภาพรวม · ต้องตามวันนี้ · อัปโหลดไฟล์ · จัดกลุ่มแท็ก ตามต้นแบบ
- ตัวกรองเพจ (ทุกเพจ = ผลรวมของ 4 เพจ) และช่วงเวลา: วันเดียว, 7 วัน, 30 วัน, เดือนนี้, กำหนดเอง
- เทียบกับช่วงก่อนหน้าที่ยาวเท่ากัน (เช่น 7 วันนี้ vs 7 วันก่อน)
- กราฟแนวโน้มรายวันจากข้อมูลจริง
- กลุ่มโฆษณา: แท็กที่เป็นตัวเลขยาว ≥ 12 หลักเข้ากลุ่ม "โฆษณา" อัตโนมัติ ตั้งชื่อเรียกในเว็บได้
- อัตราปิดแยกตามสินค้า, ลูกค้าใหม่/เก่า, ข้อความแรก — แสดงเมื่อมีไฟล์ข้อความต่อเนื่องอย่างน้อย 2 วัน (ข้อ 6.3)

**ไม่มีใน v1**
- ระบบล็อกอินรายคน (ผู้ใช้เลือกไม่เอา) — ดูได้ทุกคนที่มีลิงก์ การบันทึกต้องใช้รหัสอัปโหลด
- ดึงข้อมูลจาก Pancake อัตโนมัติ (ต้องอัปโหลดไฟล์เอง)
- วัดเวลาตอบของแอดมิน (ไฟล์ข้อความมีแค่ข้อความลูกค้า)

## 3. สถาปัตยกรรม

```
เบราว์เซอร์ (React SPA บน Vercel)
  ├─ อ่าน xlsx ในเบราว์เซอร์ → แปลงเป็นข้อมูลสรุป (ตัดข้อมูลส่วนตัวทิ้งตรงนี้)
  ├─ อ่าน: Supabase (anon key, RLS อ่านได้อย่างเดียว)
  └─ เขียน: เรียก RPC ใน Supabase พร้อมรหัสอัปโหลด → RPC ตรวจรหัสแล้วเขียน
Supabase Postgres (โปรเจกต์ใหม่ hylme-admin, org "hylme test")
```

- Vite + React + TypeScript, กราฟวาดด้วย SVG/CSS เอง (ไม่ใช้ไลบรารีกราฟ)
- อ่าน Excel ด้วย SheetJS (ติดตั้งจาก cdn.sheetjs.com เวอร์ชัน 0.20.x เพราะตัวบน npm เก่าและมีช่องโหว่)
- `@supabase/supabase-js` สำหรับอ่านและเรียก RPC
- โค้ดเก็บใน GitHub (private) เชื่อม Vercel ให้ deploy เองเมื่อ push
- วันที่ทั้งหมดใช้เวลาไทย (Asia/Bangkok)

แบ่งโค้ดเป็นหน่วยที่ทดสอบแยกได้:
- `parse/` อ่านไฟล์ → ข้อมูลกลาง (ไม่รู้จัก Supabase)
- `grouping/` กฎจัดกลุ่มแท็ก
- `metrics/` คำนวณตัวเลขทุกตัวบนหน้า จากข้อมูลกลาง (ฟังก์ชันล้วน)
- `data/` อ่าน/เขียน Supabase
- `ui/` หน้าจอ

## 4. ข้อมูลในฐานข้อมูล

| ตาราง | คีย์ | คอลัมน์ | ใช้ทำอะไร |
|---|---|---|---|
| `tag_daily` | (day, page_id, tag) | color, count | จำนวนแชทที่ติดแท็กนั้นในวันนั้น จากไฟล์สถิติแท็ก |
| `tag_groups` | tag | grp, ad_name, updated_at | กลุ่มของแท็ก และชื่อเรียกแอด |
| `conversations` | (day, conversation_id) | page_id, first_at, last_at, msg_count, first_kind, has_phone, tags text[], pancake_url | แชทที่ลูกค้าทักในวันนั้น พร้อมแท็ก ณ ตอน export |
| `conv_tag_seen` | (conversation_id, tag) | first_day, baseline bool | วันแรกที่เห็นแท็กนั้นในแชทนั้น (ข้อ 6.3) |
| `uploads` | id | uploaded_at, kind, file_name, day_from, day_to, page_ids, rows | ประวัติการอัปโหลดและปฏิทิน |
| `settings` | key | value | เก็บ hash ของรหัสอัปโหลด (อ่านไม่ได้จากหน้าเว็บ) |

- `first_kind` = `button` (ข้อความสั้นสำเร็จรูป เช่น "สนใจ", "ราคา"), `typed`, หรือ `media` (ไม่มีข้อความ เช่น ส่งรูป)
- ไม่เก็บ: ชื่อผู้ส่ง, รหัสผู้ส่ง, เนื้อหาข้อความ, เบอร์โทร, ผู้ใช้ที่ได้รับมอบหมาย, หมายเหตุ
- อัปโหลดวัน+เพจเดิมซ้ำ = ลบของเดิมของวัน+เพจนั้นแล้วเขียนใหม่ทั้งหมด (ในทรานแซกชันเดียว)

## 5. การอ่านไฟล์

**ไฟล์สถิติแท็กแบบแยกเพจ** (`pages_statistics_tag_*.xlsx`)
- ใช้ชีตที่ชื่อเป็น ID เพจ ข้ามชีตที่ลงท้าย ` today` (รายชั่วโมง)
- หาแถวหัวตาราง `ID, name, color, total, dd/mm…` แต่ละคอลัมน์ `dd/mm` คือหนึ่งวัน (ไฟล์หนึ่งมีได้หลายวัน)
- ปีเอาจากแถว "ช่วงเวลาดาวน์โหลด" ถ้าช่วงข้ามปีให้ไล่ตามลำดับคอลัมน์
- ช่องว่าง = 0
- ไฟล์แบบรวมทุกเพจ (ชีต "ทุกหน้า") → ไม่รับ แจ้งให้ export แบบแยกเพจ เพื่อไม่ให้นับซ้ำ

**ไฟล์ข้อความ** (`EXPORT_MESSAGE_*.xlsx`)
- อ่านทุกชีต ใช้คอลัมน์ ID การสนทนา, รหัสหน้า, แทรกที่, แท็ก, มีโทรศัพท์, Link Pancake, เนื้อหาข้อความ (ใช้แค่จัด `first_kind` แล้วทิ้ง)
- รวมข้อความเป็นแชท เรียงตามเวลา `day` = วันของข้อความล่าสุดของแชทนั้น
- แท็กในไฟล์นี้คือแท็ก ณ ตอน export

ก่อนบันทึก หน้าอัปโหลดแสดงสรุปทุกไฟล์ (ประเภท, วันที่, เพจ, จำนวนแถว, แท็กใหม่ที่ยังไม่มีกลุ่ม)

## 6. ตัวเลขบนหน้าเว็บ

### 6.1 จากไฟล์สถิติแท็ก (ตัวเลขหลัก)
- **แชทใหม่** = จำนวนของแท็กวันที่ของวันนั้น (เช่น `29/10` ในวันที่ 29 ต.ค.)
- **ปิดการขาย** = แท็ก `ปิด`
- **อัตราปิด** = ปิด ÷ แชทใหม่ (ระบุบนหน้าว่ารวมลูกค้าเก่าที่ปิดวันนั้น)
- **พร้อมสั่ง** = `5.พร้อมสั่ง` · **รอตามต่อ** = `ไม่เปิดอ่าน` + `อ่านไม่ตอบ`
- **ลูกค้าติดตรงไหน** = ผลรวมแท็กตามกลุ่มขั้นตอน และ % ของแชทใหม่
- ช่วงหลายวัน = ผลรวมของแต่ละวัน

### 6.2 จากไฟล์ข้อความ (สถานะปัจจุบัน)
- แชทค้างแต่ละขั้น × ลูกค้าตอบหรือยัง, ใครทักเข้ามา (ใหม่/เก่า/อื่น), ช่วงเวลาที่ทัก
- **ต้องตามวันนี้** = แชทในไฟล์ล่าสุดของแต่ละเพจที่ขั้นเป็น พร้อมสั่ง/ลังเล/ขอโปร/ขอราคา, ยังไม่มีแท็ก `ปิด` และมี `ไม่เปิดอ่าน` หรือ `อ่านไม่ตอบ`
  เรียง: พร้อมสั่ง → ลังเล → ขอโปร → ขอราคา แล้วอ่านไม่ตอบก่อนไม่เปิดอ่าน

### 6.3 อัตราปิดรายกลุ่ม (ต้องมีไฟล์ข้อความหลายวัน)
แท็กในไฟล์ข้อความไม่บอกวันที่ติด เลยใช้ `conv_tag_seen`:
- ไฟล์ข้อความแรกของแต่ละเพจ: แท็กทุกตัวถูกบันทึกเป็น `baseline` (ไม่รู้วันจริง)
- ไฟล์ถัดไป: แท็กที่เพิ่งปรากฏในแชทนั้น → `first_day` = วันของไฟล์นั้น
- อัตราปิดรายกลุ่มนับเฉพาะแชทที่เริ่มในช่วงที่เลือก และ `ปิด` ที่ไม่ใช่ baseline
- ถ้าข้อมูลไม่พอ (ต่ำกว่า 2 วันต่อเนื่อง) แสดงข้อความอธิบายแทนตัวเลข

## 7. การจัดกลุ่มแท็ก

ลำดับกฎ (ตัวแรกที่ตรงชนะ):
1. ที่ผู้ใช้เลือกไว้ใน `tag_groups`
2. รูปแบบ `d/m` → วันที่ (ซ่อนจากรายการ)
3. ตัวเลขล้วน ≥ 12 หลัก → โฆษณา
4. ขึ้นต้นด้วยเลข: 1,4 เริ่มสนใจ · 2,3,7 ติดเรื่องราคา · 6 ลังเล · 5 พร้อมสั่ง · 8,9,10 ที่มาลูกค้า
5. ตามชื่อ: ปิด → ปิดการขาย · รอ/ตรวจสอบ/ยกเลิก/โอนเงินคืน → ออเดอร์ค้าง · ไม่เปิดอ่าน/อ่านไม่ตอบ → เงียบหาย · ทักซ้ำไม่ซื้อ/ไม่สนใจ → ไม่ซื้อ · โอน/ปลายทาง → การชำระเงิน · รอสะสมแต้ม/สะสมแต้มแล้ว → สะสมแต้ม · นุ่น🤍/พี่ก้อย → แอดมิน · มะกอก/เดลี่ ออยล์/Gluta/Magnesium → สินค้า · ความดัน/อาการชา/เบาหวาน/ไขมัน → เรื่องสุขภาพ
6. ไม่ตรงอะไร → ยังไม่จัดกลุ่ม (ขึ้นเตือนในหน้าอัปโหลดและเมนู)

## 8. ความปลอดภัยและความเป็นส่วนตัว

- ทุกคนที่มีลิงก์อ่านได้ทุกหน้า ข้อมูลที่อ่านได้ไม่มีข้อมูลส่วนตัว ลิงก์ Pancake ต้องล็อกอิน Pancake ถึงเปิดได้
- RLS: ตารางข้อมูลอ่านได้อย่างเดียว, `settings` อ่านไม่ได้เลย
- การเขียนทั้งหมดผ่าน RPC แบบ `security definer` ที่ตรวจรหัสอัปโหลดด้วย `crypt()` (pgcrypto) ทุกครั้ง
- รหัสอัปโหลดตั้งโดยเจ้าของ ส่งให้แอดมินเอง เปลี่ยนได้ด้วยคำสั่ง SQL หนึ่งบรรทัด
- จำกัดขนาดไฟล์ 20 MB ต่อไฟล์

## 9. ข้อผิดพลาดที่ต้องรับมือ

- ไฟล์ผิดประเภท / หาหัวตารางไม่เจอ / ไม่ใช่เพจของ Hylme → บอกชื่อไฟล์และเหตุผล ไฟล์อื่นยังบันทึกได้
- รหัสผิด → ไม่บันทึกอะไรเลย บอกให้ลองใหม่
- อัปโหลดวันเดิมซ้ำ → แจ้งก่อนว่าจะทับของเดิม
- เน็ตหลุดระหว่างบันทึก → RPC ทำในทรานแซกชันเดียว ไม่มีข้อมูลครึ่งๆ
- Supabase โปรเจกต์ฟรีหยุดเองถ้าไม่มีคนใช้ 7 วัน → หน้าเว็บแสดงข้อความให้เปิดใหม่ (การใช้ทุกวันกันเรื่องนี้ได้)

## 10. การทดสอบ

- Vitest ทดสอบ `parse/`, `grouping/`, `metrics/` ด้วยไฟล์ทดสอบที่สร้างขึ้นเอง (ไม่ใช้ไฟล์จริงที่มีข้อมูลลูกค้า)
- สคริปต์ตรวจตัวเลขกับไฟล์จริงในเครื่อง (ไม่ขึ้น git) ต้องได้ตัวเลขเดียวกับที่ตรวจไว้ 30 ต.ค.
- ทดสอบ RPC: รหัสผิดเขียนไม่ได้, อัปโหลดซ้ำทับได้, anon key เขียนตรงไม่ได้
- ลองอัปโหลดไฟล์จริงบนเว็บที่ deploy แล้ว เทียบตัวเลขกับต้นแบบ

## 11. การ deploy

- เว็บเปิดสาธารณะ: พนักงานเปิดลิงก์ได้เลยไม่ต้องล็อกอิน (ผู้ใช้หลักคือพนักงาน ไม่ใช่เจ้าของ)
- โค้ดเก็บเป็น git ในเครื่องนี้ ไม่ต้องขึ้น GitHub (ผู้ใช้ต้องการแค่ตัวเว็บ) ขึ้น GitHub ทีหลังได้ถ้าต้องการ
- Supabase: สร้างโปรเจกต์ใหม่ `hylme-admin` ใน org "hylme test" (แพ็กเกจฟรี) ภูมิภาคสิงคโปร์
- Vercel: บัญชีส่วนตัว deploy จากเครื่องนี้ด้วย Vercel CLI, ตั้ง `VITE_SUPABASE_URL` และ `VITE_SUPABASE_ANON_KEY`
- ได้ลิงก์แบบ `hylme-admin.vercel.app` (เปลี่ยนเป็นโดเมนตัวเองได้ภายหลัง)
- ข้อควรรู้: แพ็กเกจฟรีของ Vercel (Hobby) เขียนไว้ว่าใช้ส่วนตัว ไม่ใช่เชิงพาณิชย์ ถ้าใช้ในบริษัทระยะยาวควรอัปเป็น Pro หรือย้ายไป Cloudflare Pages (ฟรี ใช้เชิงพาณิชย์ได้) — เว็บเป็นไฟล์ static ย้ายได้ไม่ต้องแก้โค้ด
